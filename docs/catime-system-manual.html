CuteHeart Exosystems — catime Brief

catime — Computational Adjusted Time

A pure base-100 time-of-day clock, written directly in AArch64 and x86-64 assembly. It slices the real day into 100 hours × 100 minutes × 100 seconds, converts between real and "cat" units through one exact integer ratio, and does the whole thing in a handful of instructions per call.

The premise is deliberately small: keep the day as the wall-clock anchor — one cat-day equals one real day — and make everything below the day decimal. A cat time-of-day is therefore a single six-digit integer HHMMSS in the range 0 … 999999 that self-segments by base-100: 152030 reads as 15:20:30 cat with no separators needed. That representation is what makes the library fast — the hot paths are just multiplies, one reciprocal multiply for the division, and a table lookup for formatting.

catime is one of the base libraries of the cutestack workspace. It has no sibling dependencies; it links only against libc (on the macOS side) or nothing at all (on the Linux fixed-interval side). Everything described here was read out of the source in this repository — the two C headers, four library .s files, two CLI/demo .s files, and the Makefile.

How to read this document

This is an explainer, not a checklist. Each section describes what a piece of code is, how it works, and — where the source makes the reasoning legible — why it is built that way. Every function, constant, register choice, and flag named here was read from the assembly or headers in this repo; nothing is invented.

The repo ships two independent libraries that share a conversion ratio but nothing else:

  • libcatime (catime.h, lib_arm64.s, lib_x86.s) — the macOS Mach-O base API. Links libc for clock_gettime. Adds "detached mode", a developer-driven synthetic timebase.
  • libcatime_fixed (catime_fixed.h, lib_fixed_arm64.s, lib_fixed_x86.s) — a Linux ELF, pure-syscall PTP-style fixed-interval timing kit. No libc, no globals.

Two standalone programs demonstrate them: the macOS catime CLI (main.s / main_x86.s) and the Linux catime-fixed spin-tick emitter (main_fixed.s / main_x86_fixed.s). Use the maturity chips (stable partial stub) throughout to gauge how finished each piece is.

The base-100 model

catime drops 60 and 24 from clock semantics. The day is divided evenly into a decimal hierarchy:

100 cat-s   = 1 cat-min
100 cat-min = 1 cat-hr
100 cat-hr  = 1 cat-day
  1 cat-day = 1 real day        <- the wall-time anchor

So a full cat-day is 100 × 100 × 100 = 1,000,000 cat-seconds, versus a real day's 24 × 60 × 60 = 86,400 real seconds. Because the day boundary is shared, the cat clock and the wall clock roll over to midnight at exactly the same instant; only the sub-day subdivision differs.

A consequence worth internalising: a cat-minute is shorter than a real minute. Concretely (from the README's unit table):

unitreal durationnote
1 cat-day86,400 s= 1 real day (anchor)
1 cat-hour864 s14 min 24 s real
1 cat-minute8.64 s—
1 cat-second0.0864 s—

The intuition trap is trying to map "cat-minute" onto "minute". Don't. The correct mental model is a pure rescale of the time-of-day axis: cat_flat = real_sec_of_day × 1,000,000 / 86,400. Everything in the library follows from that single relationship.

The 625:54 ratio

The rescale factor 1,000,000 / 86,400 reduces exactly. Both numbers share a greatest common divisor of 1600:

1,000,000 / 1600 = 625
   86,400 / 1600 =  54

cat_seconds  = real_seconds × 625 / 54
real_seconds = cat_seconds  ×  54 / 625

This is the whole numerical heart of the system. Because the ratio is a pair of small integers with a clean reduction, the conversion is exact for any consistent unit — seconds, milliseconds, or nanoseconds — and never needs floating point. ct_real_to_cat, cf_to_cat_ns, the CLI's forward path, and the fixed emitter's cat_ns computation are all the same multiply-by-625-then-divide-by-54; they just operate on different units.

The reverse direction (× 54 / 625) is integer-truncating, so a real → cat → real round-trip can lose up to a fractional cat-second. This is documented in the README as expected behaviour, not a bug: the library is integer-only by design because that is what keeps it in the sub-nanosecond cost class.

Architecture — pipeline & layers

Every catime operation is a short pipeline over 64-bit unsigned integers. There is no allocation, no state machine, and (in the base arithmetic) no branches. The layers below decompose the system from raw clock read down to a printable string.

01
Clock source
Either the hardware wall clock (clock_gettime(CLOCK_REALTIME) via libc on macOS, or a raw SYS_clock_gettime syscall on Linux) or, in detached mode, a developer-driven counter in BSS.
02
Day reduction
sec_of_day = unix_sec % 86400. Strips the epoch so only the time-of-day survives. Done with a single udiv/msub (arm) or divq (x86).
03
Ratio conversion
cat = real × 625 / 54. The /54 is a magic-multiply (umulh + lsr #5) in the optimised paths, a plain divide elsewhere.
04
Base-100 decompose
h = flat/10000, m = (flat/100)%100, s = flat%100. Pure udiv/msub. The inverse, pack, is two fused multiply-adds.
05
Format
The _fmt_hms routine turns three base-100 components into "HH:MM:SS\0" using a 200-byte two-digit lookup table — no snprintf, ~10 instructions.
06
Emit
macOS CLI hands buffers to libc printf; the Linux fixed demo assembles a line by hand and writes it with a raw SYS_write syscall.

The two libraries occupy the same layers but make opposite ABI choices. libcatime is a good citizen of the platform: Mach-O objects that call into libc, so ct_now_* inherits NTP corrections for free. libcatime_fixed refuses libc entirely: it issues syscalls directly (svc #0 / syscall) so it can be linked into a -nostdlib ELF and cross-compiled from Apple's clang with no extra toolchain.

Magic-multiply division

The division by 54 in the forward conversion is the one place the code spends real cleverness. A hardware divide (udiv / divq) is correct but comparatively slow, so the optimised paths replace x / 54 with a multiply by a 64-bit "magic" reciprocal, taking the high half of the 128-bit product and shifting:

; arm64  (lib_arm64.s, ct_real_to_cat)
mov   w9, #625
mul   x0, x0, x9                 ; x0 = real * 625
movz  x9, #0x425F
movk  x9, #0x097B, lsl #16
movk  x9, #0x25ED, lsl #32
movk  x9, #0x97B4, lsl #48       ; x9 = 0x97B425ED097B425F  (magic for d=54)
umulh x0, x0, x9                 ; high 64 of the 128-bit product
lsr   x0, x0, #5                 ; >> 5  -> exact floor(x/54)
ret
; x86_64 (lib_x86.s, ct_real_to_cat) — same constant, same shift
imulq   $625, %rdi, %rax
movabsq $0x97B425ED097B425F, %rcx
mulq    %rcx                     ; rdx:rax = rax * rcx  (rdx = high 64)
shrq    $5, %rdx
movq    %rdx, %rax
retq

The constant 0x97B425ED097B425F and the >> 5 are the exact multiply-by-reciprocal sequence a C compiler emits for /54 at -O3; the author lifted them by hand so the assembly matches what the optimiser would have produced. The README measures this at roughly 40% faster than the corresponding hardware divide for case (a). The reverse direction (× 54 / 625) keeps a plain divide, because it is not on the hot display path and the code favours clarity there. The same magic constant reappears verbatim in the fixed library's cf_to_cat_ns and inside the CLI's bench loop — one reciprocal, reused everywhere the ratio is applied.

The digit-pair formatter

_fmt_hms (in main.s / main_x86.s) converts three already-decomposed base-100 components into the nine bytes "HH:MM:SS\0" without a single call. It leans on a 200-byte lookup table, digit_pairs, that stores the ASCII rendering of every value 00…99 back to back:

digit_pairs:
    .ascii "00010203040506070809"
    .ascii "10111213141516171819"
    ... through ...
    .ascii "90919293949596979899"

Because each component is already in 0…99, its two-character rendering is just the halfword at digit_pairs + value*2. The routine loads that halfword, stores it, drops a ':' between fields, and writes a terminating NUL — about ten instructions total. The README credits this trick with cutting decompose-plus-format from ~85 ns (the old snprintf("%02lld:%02lld:%02lld", …)) to ~2 ns, roughly a 40× win, and notes it as a "good coding" flourish rather than a necessity — the formatter was never the bottleneck, but it is nearly free to make fast.

One subtlety in the comment: the routine is documented as preserving x0…x3 "as a side-effect since they're read once at top". It uses scratch registers x4…x7 and never spills, so it is safe to call in a tight loop with no frame setup.

libcatime — the macOS base API

Files: catime.h, lib_arm64.s (Darwin arm64), lib_x86.s (Darwin x86-64, AT&T syntax). Both assemble to Mach-O objects (lib_arm64.o, lib_x86.o) that you link straight into a C program. The two arches are line-for-line equivalent; only the register conventions and division encodings differ.

What it owns

Six arithmetic/clock entry points plus four detached-mode controls. The arithmetic quartet — ct_real_to_cat, ct_cat_to_real, ct_pack, ct_split — is stateless and branchless. ct_pack is the tidiest example of the style: the flat integer h*10000 + m*100 + s is computed as ((h*100)+m)*100+s with two fused multiply-adds (madd) on arm, or two imul/add pairs on x86. ct_split is its inverse and is the one arithmetic routine that takes pointers — it writes *h, *m, *s back through x1/x2/x3 (arm) or, on x86, first copies the pointer args into r8/r9/r10 because rdx/rcx are clobbered by divq.

The clock trio

ct_now_unix_sec, ct_now_unix_ns, and ct_now_cat_flat are the only functions that touch the outside world. Each begins by loading the mode byte from BSS and branching:

  • Detached → return the synthetic counter with a single load. ct_now_unix_ns lifts that seconds counter to nanoseconds by multiplying by 1,000,000,000 (the literal 0x3B9ACA00 assembled with a movz/movk pair). The result is linear and deterministic — the header calls this a "scalar lift".
  • Attached → set up a frame, call libc clock_gettime(CLOCK_REALTIME, &ts), and read tv_sec (and, for the ns variant, fold in tv_nsec with a madd).

ct_now_cat_flat composes the pipeline: call ct_now_unix_sec, reduce mod 86400 to a second-of-day, then tail into ct_real_to_cat. Because it reuses the other two entry points it inherits detached-mode behaviour automatically — a detached ct_now_cat_flat is fully deterministic.

Note one header/README mismatch worth flagging: ct_now_unix_ns is declared in catime.h and implemented in both .s files, but the README's "libcatime C API" listing omits it. The function is real; the doc list is just incomplete.

Detached mode — the virtual crystal

Detached mode swaps the clock source from hardware to a developer-driven counter, turning libcatime into a synthetic timebase you can speed up, pause, or rewind while the format/decompose/convert pipeline keeps working unchanged. It is the library's most distinctive feature and its entire state is two 8-byte cells in BSS:

.section __DATA,__bss
.lcomm _ct_mode,    8    ; 0 = attached, 1 = detached
.lcomm _ct_counter, 8    ; detached: current unix-sec value

The four controls

  • ct_detach(start_unix_sec) — store the anchor into _ct_counter and set _ct_mode = 1.
  • ct_attach() — clear _ct_mode back to 0 (str xzr on arm, movq $0 on x86).
  • ct_tick(delta_sec) — add delta to the counter, but only when detached. The routine loads the mode and cbz/je-skips the whole body if attached, so calling it in attached mode is a safe no-op.
  • ct_is_detached() — return the mode byte directly as the int result.

Why it is built this way

The README lists four motivations, all traceable to the code: (1) warp-speed simulation — because cat-time is a pure 0…1,000,000 counter, you can walk an entire cat-day at memory bandwidth; (2) deterministic benchmarking — no NTP drift, same input → same trace; (3) black-box replay — feed persisted values back into a detached emitter to step through history; (4) zero overhead when off. Point (4) is legible in the assembly: attached mode adds exactly one cmpq/cbz against a single byte, branch-predicted not-taken, so detached support costs the hot attached path essentially nothing. The detached ct_now_unix_sec is a lone load from BSS — the README clocks it near 1 GOps/s, which is the upper bound on how fast a simulation can step through cat-time.

libcatime_fixed — PTP-style fixed-interval timing

Files: catime_fixed.h, lib_fixed_arm64.s, lib_fixed_x86.s. This is a completely separate library aimed at Linux hosts doing lock-stepped, absolute-grid timing (the header frames the motivating use as HFT). It is compiled -nostdlib and issues syscalls directly, so it drops into an ELF with no libc.

Clock read — cf_now_ns

Loads CLOCK_REALTIME via a raw clock_gettime syscall (x8 = 113 on arm64, rax = 228 on x86-64 — the two Linux syscall numbers differ, which is why each arch hard-codes its own .equ SYS_clock_gettime). It then folds the returned tv_sec/tv_nsec into a single nanosecond count with the same × 1e9 + nsec multiply-add used everywhere else. The clock is assumed to be disciplined upstream by ptp4l or chrony against a NIC PHC, giving sub-microsecond accuracy on a properly configured host.

Conversion & grid

  • cf_to_cat_ns — identical magic-multiply as ct_real_to_cat, applied to nanoseconds instead of seconds (the ratio is unit-agnostic).
  • cf_from_cat_ns — the × 54 / 625 reverse with a plain divide.
  • cf_next_grid_ns(now, interval) — the smallest k·interval strictly greater than now, computed as (now/interval + 1) × interval. Used to align ticks to an absolute wall-clock grid so multiple hosts fire in lock-step.
  • cf_wait_until_ns(target) — busy-spins on cf_now_ns until the sample reaches target, then returns the actual observed value. The positive gap observed − target is the per-tick "drift" of your spin loop.

The API is deliberately caller-managed — no init call, and (per the header) "no globals". In practice the assembly keeps one shared .bss timespec scratch (cf_ts) that the syscall writes into; it is reused across calls rather than passed by the caller. This is fine for single-threaded use but is the one spot where the header's wording runs slightly ahead of the code (flagged under Limitations).

catime CLI — the macOS front end

Files: main.s (arm64), main_x86.s (x86-64). A self-contained Mach-O executable that links libc (for printf, strcmp, atoll, clock_gettime, mach_absolute_time). _main dispatches on argv[1] by string-comparing against a fixed set of subcommand literals, then falling through to numeric conversion.

invocationdoes
catime <real_seconds>forward: prints real: and catime: (× 625 / 54).
catime -r <cat_seconds>reverse: prints catime: and real: (× 54 / 625).
catime nowreads CLOCK_REALTIME; prints unix sec, real HH:MM:SS (mod 60/60/24), cat HH:MM:SS (base-100), and catime_flat.
catime split <flat>decomposes a flat integer to base-100 H, M, S and the formatted hms string.
catime pack <H> <M> <S>composes H, M, S into a flat integer.
catime benchruns the microbenchmark battery.
(no / bad args)prints usage_str and exits 1.

The bench battery

The Lbench path times five cases against CLOCK_MONOTONIC (chosen deliberately over CLOCK_REALTIME so clock slewing can't perturb the elapsed measurement — the README calls this out). The cases:

  • (a) 100M iterations of the magic-multiply conversion.
  • (b) 1M iterations of cat decompose (three mod-100 steps) + _fmt_hms.
  • (b') 1M iterations of the real decompose (mod-60/60/24) + format, as an apples-to-apples control. The README notes (b) and (b') come out identical because arm64 udiv is constant-time regardless of divisor — base-100 is not intrinsically faster than base-60.
  • (c) 1M clock_gettime calls.
  • (c') 1M mach_absolute_time calls — the lower-overhead clock read, shown for contrast.

A summary block then contrasts a live real-clock at 1 Hz (per-tick = b' + c) against a live cat-clock at its native 11.574 Hz cadence (per-tick = a + b + c, scaled by the ratio to ns/s), reporting each as a parts-per-billion fraction of one core. The headline conclusion: per display update, catime is indistinguishable from a regular wall clock; the whole steady-state difference is just the higher tick rate.

catime-fixed demo — the Linux spin-tick emitter

Files: main_fixed.s (arm64), main_x86_fixed.s (x86-64). A pure-syscall Linux ELF (entry _start, no libc) that demonstrates the fixed-interval spin-tick pattern. Invocation:

./catime-fixed <interval_ns> [iters]     # iters defaults to 10

It anchors on CLOCK_REALTIME, computes the first grid target as ceil(start / interval) × interval, then loops: spin on _read_realtime_ns until the clock crosses the target, compute drift = observed − target and cat_ns = observed × 625 / 54, format one line, and SYS_write it to stdout. Each line reads:

tick=N ptp_ns=N cat_ns=N drift_ns=N

Because it cannot use libc, the demo carries its own tiny helpers: _atoi (parse the args, no error handling — it stops at the first non-digit), _u64_str (write a u64 as decimal then reverse the digits in place), _emit_label (a byte-copy for the literal field names), and _write_buf (the raw write syscall). The header comment is candid that the spin uses the syscall clock (~500 ns/call) and that production HFT would link the vDSO __vdso_clock_gettime (~25 ns) for a ~20× lower spin overhead — a swap the library is structured to make easy but does not perform itself.

Build system

The Makefile has four meaningful targets. Everything builds with Apple-shipped clang — no cross toolchain — because clang can retarget via -arch (Mach-O) and -target … -nostdlib (Linux ELF).

targetbuildscommand shape
make / allcatime (arm64) + catime-x86 (x86-64) CLI toolsclang -arch arm64 -o catime main.s
make apilib_arm64.o, lib_x86.o (Mach-O base library)clang -arch arm64 -c lib_arm64.s
make liblib_fixed_arm64.o, lib_fixed_x86.o (Linux ELF)clang -target aarch64-linux-gnu -nostdlib -c …
make cleanremoves binaries, .o files, .dSYM dirs—

The x86-64 CLI is built for macOS and runs under Rosetta on Apple Silicon; the README's x86 benchmark numbers are Rosetta-translated, so native x86 hardware would be modestly faster. CLI tools and the base API link libc; the fixed-interval library is pure-syscall. Committed .o files exist in the tree, but .gitignore excludes the CLI binaries (catime, catime-x86), all *.o, and *.dSYM/ from future commits.

catime is one of the four base projects of the cutestack workspace, alongside xcess, pompom, and cutecontainer. It has no sibling dependencies — it is a leaf that others may consume, not a composite.

Current limitations

An honest accounting of what is unfinished, approximate, or caveated — read directly from the source and its comments.

Syscall clock, not vDSO partial

cf_now_ns and the demo's _read_realtime_ns use the raw clock_gettime syscall (~500 ns/call per the comments). Production HFT latency (~25 ns) requires linking the host's vDSO __vdso_clock_gettime. The code is structured to make that a near one-instruction swap, but it does not do it.

Fixed-interval clock-read cost is Linux-only partial

The conversion kernels are now measured — make bench reports ~2.8 ns/op for the magic-mul forward path and ~5.1 ns/op for the rounded reverse divide on Apple M-series, and those routines are instruction-identical to the Linux cf_to_cat_ns/cf_from_cat_ns. The cf_* ELF kernels are also now executed natively (not merely cross-assembled from macOS): make test-linux runs tests/test_catime_linux.c against the real lib_fixed_{x86,arm64}.s objects on x86_64 and aarch64 Linux in CI, so correctness is verified on-target. What still can't be measured from macOS is cf_now_ns's raw clock_gettime syscall (~500–800 ns), a Linux kernel-entry cost.

"No globals" wording vs. shared BSS scratch partial

catime_fixed.h advertises "caller-managed state (no globals, no init)", but cf_now_ns writes into a shared .bss timespec (cf_ts). Harmless single-threaded, but it is process global state and is not thread-safe as written.

Reverse conversion is now correctly rounded fixed

The reverse path (ct_cat_to_real / cf_from_cat_ns) now adds 625/2 = 312 before the divide, so × 54 / 625 rounds to nearest instead of truncating. real → cat → real is exact over the tested range (worst error 0), and the residual cat → real → cat error (≤ 6) is the unavoidable lattice slack — real is the coarser unit (~11.57 cat per real) — not a rounding defect. Proven by make test.

Platform split is intentional

Not a limitation so much as a boundary: libcatime targets macOS Mach-O and links libc; libcatime_fixed targets Linux ELF and refuses libc. There is no single object that does both, and the ct_* and cf_* namespaces do not interoperate beyond sharing the 625:54 ratio.
