Base-100 time-of-day on an
exact 625:54 integer lattice.

catime slices the day into 100 hours × 100 minutes × 100 seconds — a flat 6-digit HHMMSS that self-segments by base-100 — and converts to and from wall time with a single reduced integer ratio, 625/54. The four instruments below are the actual arithmetic: the conversion lattice and its round-trip residue, decimal self-segmentation against base-60, the fixed-interval PHC grid that keeps hosts in lock-step, and the detached "virtual crystal" that warps a whole cat-day into a quarter-millisecond. Each plot is computed from the same arithmetic the asm runs.

Scope. Every plotted value is computed live from catime's own integer rules (seeded RNG only drives jitter/offsets), reproducing the qualitative regime. Ratios, byte layout, and API names are taken verbatim from catime.h, catime_fixed.h, and the arm64/x86_64 cores lib_arm64.s / lib_fixed_x86.s. Where clock jitter is illustrative it is labelled schematic.

I conversion · why real→cat→real is exact but cat→real→cat is not

One reduced ratio, 625:54, and the lattice it defines over the day.

The conversion rests on one identity: 1 day = 86,400 real s = 1,000,000 cat s, and gcd(86400, 1000000) = 1600, so the map is the reduced ratio 625/54. Forward (ct_real_to_cat) is a truncating ×625/54; reverse (ct_cat_to_real) adds 625/2 before the /625 divide — it is correctly rounded. Because one real second spans 625/54 ≈ 11.574 cat units, the mapping is a staircase, not a line: many cat values share a real second.

cat = ⌊real·625/54⌋  ·  real = ⌊(cat·54 + 312)/625⌋  ·  real→cat→real = identity,   cat→real→cat drifts ≤ ~6

II format · a flat integer that decomposes by mod-100

HHMMSS self-segments by mod-100: the day sliced decimally vs sliced by 60.

A cat time-of-day is a single integer in 0…999,999. ct_pack is h·10000 + m·100 + s; ct_split peels it back with three mod-100 steps — so 152030 is 15:20:30 cat, no separators. The real clock nests three different radices (/60, /60, /24); catime nests one. The strips below place every hour boundary of each scheme on the same day axis: cat-hours are 864 s apart and evenly spaced; real-hours are 3600 s apart — the two grids are incommensurate, which is exactly why you must treat cat time-of-day as real × 1,000,000 / 86,400 and never map "cat-minute" onto "minute".

III fixed-interval · aligning independent hosts to one wall-clock grid

cf_next_grid_ns puts every host on the same tick — if the interval clears the spread.

For PTP-grade timing, libcatime_fixed reads CLOCK_REALTIME (or a NIC's PHC via cf_open_phc → cf_phc_clockid → cf_now_dynamic_ns) and snaps to an absolute grid: cf_next_grid_ns returns the smallest k·interval strictly greater than now. Because the grid is anchored to the epoch, hosts whose clocks differ by less than one interval all compute the same next tick — lock-step without a coordinator. cf_wait_until_ns then spins to it; the overshoot it returns is the per-tick drift of that spin.

cf_next_grid_ns(now,I) = (⌊now/I⌋ + 1)·I  ·  lock-step ⇔ max|offsetᵢ − offsetⱼ| < I  ·  drift = cf_wait_until_ns(t) − t ≥ 0

IV detached · swap the hardware clock for a developer-driven counter

The virtual crystal: one cat-day, deterministic, in 0.244 ms.

ct_detach(anchor) repoints every ct_now_* from the hardware clock to a counter you ct_tick yourself. Attached, ct_now_cat_flat pays ~31 ns and inherits NTP slew and kernel jitter; detached, it's a single load from BSS — ~2.3 ns, deterministic. Stepping 86,400 cat-second ticks (one real day) measured at 0.244 ms on arm64 — a 354-million× warp factor. · invariants the implementation holds

What every conversion, format, and clock path must preserve.

§1
One ratio, reduced

All conversion is 625/54 (= 1,000,000 : 86,400 ÷ gcd 1600). Works on any consistent unit — s, ms, ns — the integer ratio doesn't care.

§2
Reverse is correctly rounded

ct_cat_to_real adds 625/2 before /625, so real→cat→real is exact over range. cat→real→cat drift is the lattice, not a bug.

§3
Flat integer self-segments

ct_pack/ct_split by mod-100; 0…999,999 reads as HHMMSS with no separators. Formatter is a 200-byte pair table, ~2 ns.

§4
The grid is absolute

cf_next_grid_ns anchors to the epoch, so hosts lock-step with no coordinator — provided the clock spread stays under one interval.

§5
Detached is deterministic

Same anchor + same ticks → byte-identical trace; zero NTP/jitter. Attached hot path is unchanged (single predicted-not-taken cmpq).

§6
Two arches, one arithmetic

arm64 + x86_64 cores compute identical results; fixed-interval kernels are byte-for-byte the base ct_* instructions. Magic-multiply, no runtime udiv.

· for researchers · open questions

Research follow-ups.

Concrete directions tied to the four instruments above. Each is an unresolved question in the current implementation, stated in terms a student could pick up.

Q1
Tight bound on cat→real→cat drift

Figure I shows the cat→real→cat residue as a sawtooth. Prove the exact worst-case bound over 0…999,999 from the truncating ×625/54 and the +625/2 reverse, rather than reading "±6" off the plot — and characterize which cat values are fixed points.

Q2
Sub-second and leap-second mapping

The 625/54 ratio is defined for a nominal 86,400 s day. Extend it to ms/ns units and specify behaviour across a leap second (86,401 s day): does the lattice re-scale, absorb the extra second, or is the day boundary redefined? Quantify the round-trip error each choice introduces.

Q3
Beat structure of the two hour-grids

Figure II shows cat-hours (864 s) and real-hours (3600 s) coinciding only at 0 and 86,400. Derive the full alignment/beat pattern (near-coincidences within a tolerance ε) and ask whether any base-100 subdivision yields a useful common grid with civil time.

Q4
Lock-step under bounded clock drift

Figure III assumes static per-host offsets under one interval. Model offsets that drift over time (skew, not just bias) and derive the interval I and re-sync period that keep cf_next_grid_ns agreement across N hosts — and the failure rate when spread crosses I.

Q5
Spin-drift model vs measured PHC reads

The drift histogram in Figure III is schematic. Replace it with measured cf_wait_until_ns overshoot from real CLOCK_REALTIME and PHC sources, and fit a model for the read-cost tail across platforms — is median drift dominated by cf_now_ns latency or by scheduler wakeups?

Q6
Detached determinism as a test oracle

Figure IV's detached counter replays byte-identically. Formalize this as a golden-trace oracle: what class of time-dependent bugs (ordering, interval boundaries, wraparound at 1,000,000) can a deterministic ct_detach → ct_tick schedule provably surface, and how should ticks be chosen?

Pipeline in one line: real seconds ×625/54 → cat flat 0…10⁶ → ct_split mod-100 → HHMMSS; fixed-interval snaps to cf_next_grid_ns and spins via cf_wait_until_ns; detach swaps the source for a counter you tick.
